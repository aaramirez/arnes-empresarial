# v3.5.0 — `autorizacion-empleado`: evidencia de cierre (post-tarea 5.2)

**Entregable funcional**: un empleado con rol base (`empleado`, el default de toda fila sin `roles_empleado`, ADR 156) que intenta resolver una solicitud interna o un reembolso escalado **ajenos** recibe **no autorizado**, distinguible de "no encontrada"/"ya resuelta", con una fila de auditoría (`resultado='no_autorizado'`) que sobrevive fuera de cualquier transacción de dominio; el mismo empleado, una vez que el CLI real le asigna `--rol administrador` **en caliente** (sin reiniciar la sesión de la TUI), puede resolver esa misma solicitud/reembolso ajenos; y ese mismo rol elevado **no** alcanza para aprobar/rechazar una solicitud **propia** — la prohibición de autoaprobación (`resultado='autoaprobacion_prohibida'`) corta antes, incluso con rol administrador. El autoservicio (`/cancelar-solicitud` sobre lo propio, con rol base) sigue intacto, sin que el gate de rol lo toque.

**Tareas**: [`openspec/changes/autorizacion-empleado/tasks.md`](../../../openspec/changes/autorizacion-empleado/tasks.md) — 5 Work Units (PR1-PR5), todas commiteadas en `hito/v3.5-autorizacion-empleado`. Esta verificación cubre el punto "Después de la tarea 5.2" del propio `tasks.md`: carpeta de progreso con evidencia, sin código de producción, previa al tag de versión.

## Cómo se corrió la demo

Mismo patrón que [`docs/progreso/v3.3-comando-cancelar-solicitud/README.md`](../v3.3-comando-cancelar-solicitud/README.md) y [`docs/progreso/v3.4-comando-visibilidad-a2a-entrante/evidencia-verificacion-manual.md`](../v3.4-comando-visibilidad-a2a-entrante/evidencia-verificacion-manual.md), con una diferencia de entorno: esta vez la carpeta throwaway vivió **fuera** del repo, bajo el scratchpad de la sesión (`.../scratchpad/demo-v3.5-autorizacion-empleado/`), nunca dentro del checkout — así que un `node_modules` propio no existía ahí; se resolvió con una **junction de directorio** (`mklink /J`) apuntando al `node_modules` real del repo, borrada junto con el resto al terminar (no copia nada, no dejó rastro).

1. Un script throwaway (`driver-v3.5.tsx`, **borrado al terminar** — no es parte del entregable; ver `driver-output-raw.log` de esta misma corrida, también borrado, para la salida cruda completa que produjo esta sección y la de evidencia).
2. SQLite **temporal** bajo el scratchpad de la sesión (`.../scratchpad/demo-v3.5-autorizacion-empleado/data/harness.db`), **nunca** `data/harness.db` real del repo — confirmado con `git status --porcelain data/` antes y después de toda la corrida: vacío en ambos casos.
3. Reusa `openDatabase`, `bootstrapHarness()`, `buildOnComandoEmpleado`, `createSolicitudStore(db)`/`createVentaStore(db)` (los stores reales de `SolicitudStorePort`/`VentaStorePort`), `hashPassword`/`verificarPassword`, `resolveAuthConfig`/`resolveVentasConfig` — todos módulos reales de `src/`, nada reimplementado ni stubeado. Única costura deliberada, igual que v3.3/v3.4: `onSubmit`/`onSoporte` son funciones que lanzan si se llaman (nunca se invocan en este guion, que sólo ejercita `/aprobar-solicitud`, `/aprobar-reembolso`, `/cancelar-solicitud`, `/login`, `/logout`) — evita costo de API ajeno al alcance de esta tarea.
4. Credenciales de `beto`/`carla`/`ana` provisionadas con el **CLI real** (`node <tsx-cli> src/empleados.ts <id>`, password por stdin, hash scrypt real, cwd = carpeta scratch para que `data/harness.db` resuelva ahí y no en el repo). El rol `administrador` de `ana` se asignó, también con el CLI real (`... src/empleados.ts ana --rol administrador`), **a mitad de la demo**, con la sesión de Ink ya montada en el mismo proceso — nunca antes de arrancarla.
5. Las solicitudes/venta de prueba se sembraron con `SolicitudStorePort.crearSolicitudConCaso`/`VentaStorePort.crearVentaConCaso`+`escalarReembolso` reales — **no** vía `/solicitar` ni el modelo: exactamente el criterio que v3.3 ya dejó documentado (sembrar con el caso de uso que invoca el modelo real hubiera sido caro y ajeno a lo que esta tarea verifica).
6. Monta `<App onSubmit={onComandoEmpleado} />` (el componente TUI real) con `render()` de `ink-testing-library`, sesión única secuencial (login/logout entre `beto`/`carla`/`ana`), reproduciendo el hallazgo ya documentado por v3.3: **dos** llamadas separadas a `stdin.write` — `instance.stdin.write(comando)` y luego `instance.stdin.write("\r")` — nunca una sola con el `\r` embebido.
7. **Hallazgo nuevo de entorno de esta sesión** (no del entregable): al importar `App.tsx` dinámicamente desde un script ubicado fuera del árbol del repo, `tsx` no auto-descubre el `tsconfig.json` del repo (`jsx: "react-jsx"`) — sin él, transforma el JSX con el pragma clásico y la TUI real explota con `React is not defined` en cuanto intenta renderizar. Se resolvió invocando `tsx` con `--tsconfig <repo>/tsconfig.json` explícito. Documentado acá porque, a diferencia del hallazgo de `stdin.write` (aplica a cualquier entorno), éste es específico de correr el driver **fuera** del árbol del repo — no aplicaba en v3.3/v3.4, que corrían su `scratch-demo/` anidado dentro del repo.

## Limpieza del entorno

- `driver-v3.5.tsx`, `driver-output-raw.log`, `package.json`/`tsconfig.json` del scratch, `mk_junction.bat` y la SQLite temporal (`data/harness.db`, `data/harness.log`) — todo bajo el scratchpad de la sesión — se borraron al terminar, junto con la carpeta completa.
- La junction `node_modules` (scratch → `node_modules` real del repo) se removió (una junction se elimina sin tocar el destino: `rmdir` sobre el punto de unión, nunca recursivo sobre el contenido real).
- `git status --porcelain data/` del repo real: **vacío antes y después** de toda la corrida — confirmado explícitamente en la sección de evidencia.
- Sin procesos `node`/`tsx` colgados propios de esta demo (el CLI de asignación de rol y el driver terminan y salen solos, sin servidor de fondo — no hizo falta levantar A2A para esta verificación).

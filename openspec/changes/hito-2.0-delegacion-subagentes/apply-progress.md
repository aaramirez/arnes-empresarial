## Deviations from Design

None for the core requirement. Task 3's migration SQL is copied verbatim from design.md §6.1 (which itself already documents, in ADR 48, the intentional deviation from the Plan's literal DDL — that deviation is pre-approved by the checkpoint, not something this batch introduced). The re-export line and both doc-comment updates from task 2 also match design.md §5.1's intent (the exact wording of the header update was not dictated verbatim by design.md, only the requirement that it stop being false — see design.md line 318).

**Task 4 — disclosed scope expansion (human-resolved before this batch, partially re-discovered during it)**: `design.md` §5.2 makes `description` mandatory on `AgentDefinition` but does not address the fallout on hand-built test doubles. The human checkpoint had already identified and pre-approved a mechanical one-line fix (`description: "agente de prueba"`) for 6 specific files. Running `npm run typecheck` after implementing task 4 showed the actual break surface was **8 files**, not 6 — `src/build-on-activity.test.ts` and `src/core/turn-selector/invoke-model.test.ts` were not on the human's list. Both use the exact same `makeAgent()` factory pattern already authorized for the other 6, so the identical fix was applied to them too rather than re-blocking the batch, and is disclosed here transparently (not silently absorbed) so the Reviewer can object if a separate explicit decision was actually wanted for these 2.

**Task 5 — disclosed content gap (systemPrompt not literally specified by design)**: design.md §5.2's table gives `description` and `allowedTools` verbatim for all four roles, but no literal `systemPrompt` text — a real gap versus task 4, where `CONVERSATIONAL_AGENT.description` was a fixed, test-asserted string. Since task 5's own acceptance test (verbatim in the assignment) does not assert an exact `systemPrompt` value, and `allowedTools`/`description` (the two fields design.md does fix precisely) were transcribed exactly as given, a second-person `systemPrompt` was written per role instead of blocking the whole task — content-equivalent to the already-fixed `description`, not new invented behavior. Four id constants (`PLANNER_AGENT_ID` etc.) were also added, not explicitly named by design.md but consistent with the pre-existing `CONVERSATIONAL_AGENT_ID` pattern. Both choices are disclosed in `tasks.md` task 5's own note for the Reviewer to confirm or correct.

**Task 6 — disclosed content gap (assembled-text format not literally specified by design)**: design.md §5.3 fixes `TAREA_DELEGADA_MAX_CHARS`, `TAREA_TRUNCADA_SUFIJO`, and every type/function signature verbatim, but does not dictate the exact string format `construirTareaDelegada` assembles from `rol`+`insumo` — only that it's "the único constructor" and that the result must be auditable. A three-section format was chosen (role header with `id`+`description`, then `insumo.instruccion`, then `insumo.material`), deliberately **excluding** `rol.systemPrompt` from the assembled text (that text already travels separately via the role's own `AgentDefinition` in `options.agents`, task 9 — duplicating it here would only widen the surface for a leak, working against the very isolation guarantee this module exists to provide). The truncation helper mirrors `activity-prompt.ts`'s existing `truncarTexto` pattern exactly (slice to the cap, then append the suffix, without budgeting the suffix into the cap) for consistency with the codebase's one other truncation precedent. Disclosed in `tasks.md` task 6's own note for the Reviewer to confirm or correct.

**Task 8 — two disclosed gaps, both already flagged above and in `tasks.md`**: (1) `Eslabon`'s shape is never declared in design.md, only used as a type name in two signatures (`despacharCadena`'s parameter, `construirEslabonesRevision`'s return type in task 11) — implemented as `{ agentId: string; insumo: InsumoDelegado }`, reusing the existing `InsumoDelegado` type rather than inventing new fields. (2) `despacharDelegacion`'s input gains an optional `destino?: DestinoDelegacion` field beyond design.md's literal signature — this is the mechanism task 7's own already-approved doc-comment previews verbatim ("se ejercita... pasándoselo directo a `despacharDelegacion`"), and is the only way to reach the `a2a` throw through the public `despacharDelegacion` function, since no real `agentId` in `SUBAGENT_REGISTRY` ever resolves to `a2a`. Neither gap changes any behavior design.md does fix precisely (the `crear → invocar → completar` order, the exact `DelegacionStorePort` method shapes, the chain-threading rule) — both are additive, disclosed, and reversible if the Reviewer prefers a different shape.
